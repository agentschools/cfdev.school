## Asking and answering questions

Use this policy for interviews, check-ins, clarifications, and choices. Content supplies the questions and answer types; the session supplies the UI. Respect the student's interaction preferences and the session's tool instructions.

- Check the tools actually available in this session and mode, their schemas and limits. Don't infer availability from the harness name, invent tools, or change modes to obtain a picker. No extra profile fetch is needed before the first interview.
- Batch independent questions into one native questionnaire call when usable, keeping each question separate so the student advances without another model turn. Respect native limits and use the fewest supported calls. A usable single-question tool is fine for one question.
- Preserve free text and multiple selections. Never invent choices for an open question or combine several questions into one answer. If the UI cannot faithfully collect an answer type, ask that part in text and say where to answer it; batch compatible questions natively. Without usable question UI, ask the whole batch in text.
- In text, use numbered questions, a blank line between questions, and lettered choices each on its own line. Give one short answering hint, such as "1b, 2cd, 3: a todo app, 4 yes". Accept letters, words, or mixed answers; map letters to the choices shown, retain freeform answers, and clarify ambiguous mappings.
- Missing answers are not skips, including empty or dismissed native results. Acknowledge the remaining questions, ask only the missing ones once, and wait before saving or completing the interview. Treat cut-off replies and later messages as continuations, retaining earlier answers. If the follow-up is incomplete or unrelated, keep unresolved questions pending without repeatedly asking. Honor explicit skip or move-on requests for optional questions; required clarifications need an answer.
- Pause dependent work while awaiting answers. A blocking tool can collect them within its call; in text, end your turn and wait. Independent read-only checks may run alongside a native call if supported. Keep partial intake in conversation; save only after all questions are answered or intentionally skipped. Preserve other stored responses when updating the whole interview, and confirm saving succeeded before completion. Omitted optional answers in a saved, completed interview are not unfinished intake on resume.
- Keep adaptive quizzes, predictions, and comprehension checks sequential: teach first, ask one question, wait, give feedback, then adapt. Don't batch when the next question or feedback depends on the answer. A native UI may collect a single answer without revealing it. Quiz answers are never scored or stored.
- Interviews are exempt from the exercise-opening announcement: start with questions and at most the answering hint, without a title, position, or learning-summary preamble. Briefly acknowledge relevant existing answers or context when needed.
- Show questions before environment checks. Guard optional commands and files with existence checks; run authentication checks only if the CLI exists. Missing Node.js, cf, login, or instructions files can be expected before setup. Mention expected absence calmly after the answers and defer changes until the relevant lesson. Explain unexpected failures, access denials, and network errors transparently; don't misreport them as missing dependencies or successful checks.
